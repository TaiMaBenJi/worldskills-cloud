## 5.1 监控体系设计（五层模型）

```
第 5 层  业务指标     订单量/登录数/响应成功率        ← 老板关心的语言
第 4 层  服务可用性   API 200 率/端口存活/证书有效期   ← 应用团队的语言
第 3 层  系统资源     CPU/内存/磁盘/网络              ← 系统管理员的语言
第 2 层  硬件健康     RAID/风扇/电源/温度/SMART        ← 机房管理者的语言
第 1 层  基础设施     市电/UPS/空调/温湿度/漏水/门禁    ← 机房管理者的语言
```

**关键认知**：机房管理者至少对 **1-3 层**负直接责任；能从第 1 层一路联想到第 5 层的影响，就是 L3+ 的思维。

### 工具选型（够用即可）

| 层 | 工具选择 |
|---|---|
| 设施 | 动环平台（厂商自带）/ SNMP 采集进主监控 |
| 硬件 | 带外轮询（ipmitool/Redfish 脚本）+ 厂商管理平台 |
| 系统/服务 | Zabbix（全能老将）或 Prometheus+Grafana（云原生） |
| 业务 | 由应用团队接入同一平台（统一告警出口） |

**统一告警出口**是设计精髓：不管哪层出事，告警都进**一个**通道（电话/短信/App），值班人不用盯五个屏幕。

### 阈值设定方法论

1. **静态阈值**（起步）：CPU>90% 持续 5 分钟——简单但粗糙
2. **动态基线**：按历史同时段对比（白天 80% 正常、凌晨 80% 异常）
3. **趋势预测**：磁盘增长斜率 → "按当前速度，18 天后满"——提前预警
4. **机房特化阈值**：温度 30/32/35°C 三档、UPS 负载 70%/80%、电池续航 <15 分钟 = 紧急

### 告警治理四原则

- **分级**：P1（立即电话）/ P2（App 推送）/ P3（日报汇总）
- **收敛**：同一故障源只发一次（抑制风暴）
- **责任**：每条告警有 Owner，无人认领的告警 = 设计错误
- **复盘**：每周看误报榜，优化阈值（告警疲劳是事故之母）

## 5.2 巡检自动化

### 三级跳

```
① 手工巡检表（纸质/电子表格）
   └─ 适合：起步期、设备少、建立清单的过程本身很有价值
② 巡检脚本（cron + 输出留档）
   └─ 适合：有 Linux 基础的机房，能覆盖系统层
③ 巡检平台（脚本 + 动环 + 监控汇聚，自动出报告）
   └─ 适合：多机房、要向上汇报的团队
```

### 综合巡检脚本模板（拿来改）

```bash
#!/bin/sh
# room-check-full.sh — 机房综合巡检（每天 8:30 由 cron 调用）
echo "════ 机房巡检报告 $(date '+%F %T') ════"

echo "── 1. 时间 ──"
date '+%F %T %Z'

echo "── 2. 磁盘 ──"
df -h 2>/dev/null | grep -vE 'tmpfs|udev' || echo "（df 不可用，检查挂载）"
echo "关键目录用量："; du -sm /srv /var/log 2>/dev/null

echo "── 3. 服务 ──"
for svc in nginx mariadb; do
  pgrep -x "$svc" >/dev/null 2>&1 && echo "OK  $svc" || echo "FAIL $svc"
done

echo "── 4. 网络 ──"
ping -c1 -W2 127.0.0.1 >/dev/null 2>&1 && echo "loopback OK"
wget -q -T2 -O /dev/null http://127.0.0.1:8081/ && echo "HTTP OK" || echo "HTTP FAIL"

echo "── 5. 最近登录 ──"
last -n 5 2>/dev/null || echo "（无 last 记录）"

echo "════ 巡检完成 ════"
```

### 巡检结果管理（比"跑脚本"更重要）

- 输出**留档**（带日期文件名），能对比"昨天/上周/上月"
- **趋势敏感**：磁盘从 40% → 43% → 47%，今天的数字本身不重要，斜率才重要
- 异常自动上报：脚本发现 FAIL 项时主动发通知（而不只是打印）

## 5.3 备份体系（机房管理者的底线）

### 先算两个数：RPO / RTO

- **RPO**（最多丢多少数据）：能接受丢 1 小时？= 备份至少每小时一次
- **RTO**（多久恢复）：4 小时恢复？= 演练过"4 小时内拉起"的方案

```
RPO=24h  → 每晚全量/增量即可
RPO=15min → 需要持续复制/快照
RTO=4h   → 本地备份 + 换机重装流程
RTO=30min → 高可用/异地热备
```

### 3-2-1 落地版

- **3 份**：生产 + 本地备份 + 异地备份
- **2 种**：如磁盘阵列 + 对象存储/磁带
- **1 异地**：物理隔离（勒索病毒会顺着网络找备份删！）

### 概念澄清

| 概念 | 是备份吗 | 说明 |
|---|---|---|
| RAID | ❌ | 防"盘坏"，不防"删库/加密/火灾" |
| 快照 | ⚠️ 算半个 | 依赖原卷，原卷损毁快照一起完蛋 |
| 同机异盘备份 | ⚠️ 太弱 | 机器被偷/被烧一起没 |
| 异地独立副本 | ✅ | 真备份 |
| **恢复演练过** | ✅✅ | 真·真备份 |

### 备份检查清单（月度）

- [ ] 所有应备份对象都在清单里（有没有漏了一台"临时"服务器？）
- [ ] 备份任务成功率 100%（失败任务逐个查明）
- [ ] 恢复演练：随机抽一个文件/一个库，实际恢复一次
- [ ] 异地副本完整性抽查（校验和比对）
- [ ] 备份介质健康（磁带轮换、磁盘 SMART）

## 5.4 容量管理（四维水位表）

| 维度 | 指标 | 警戒线 | 扩容触发 |
|---|---|---|---|
| 电力 | 已用/总量 | 70% | 80% 启动采购 |
| 空间 | U 位/机柜/面积 | 70% | 80% 规划新柜 |
| 网络 | 端口数/带宽利用率 | 70% | 80% 扩端口/升带宽 |
| 算力 | CPU/内存/存储分配率 | 70% | 80% 加节点 |

**月度容量报告**模板：四维水位 + 趋势预测（按增长率算"N 个月后触线"）+ 本期变化 + 下期建议。这份报告是机房管理者向上沟通的**核心武器**——用数据要预算，永远比"我觉得该扩容了"有效。

## 5.5 DCIM 与资产管理（从一张表开始）

**DCIM** = 数据中心基础设施管理（资产+容量+能耗+连接关系的数字化）。

**最小可行版本**（先跑起来，别等"大系统"）：

| 表 | 关键字段 |
|---|---|
| 资产表 | 设备/序列号/型号/位置(U位)/IP/管理口/维保到期 |
| 端口表 | 交换机/端口/对端设备/用途 |
| 电力表 | 机柜/PDU/插座/所接设备/功率 |
| 变更记录 | 时间/操作人/内容/原因/结果 |

**管理原则**：
- 现场动过 = 当场登记（"回头补"= 永远不补）
- 季度盘点：实物 → 表格 核对一次（找差异，找"幽灵资产"）
- 维保到期预警：提前 1 个月提醒续签/替换决策

## 5.6 变更管理与值班体系

### 变更管理（保护自己也保护业务）

```
申请（改什么/为何/影响/回滚）
  → 评审（双人复核：操作人+审核人）
  → 窗口执行（低峰期，双人在场，先备份后动手）
  → 验证（按清单逐项确认）
  → 记录（写进变更台账）+ 观察期（次日回看监控）
```

**黄金细节**：
- 回滚方案是"变更单"上最重要的一行——**写不出回滚 = 没准备好**
- 大变更先在测试环境"彩排"一次
- 变更后 24 小时不进下一个变更（留观察期）

### 值班体系

- **交接班三句话**：做了什么、发现什么、遗留什么（口头 + 记录本）
- **事件分级**：P1 立即升级（叫醒负责人）/ P2 当班处理 / P3 排期
- **升级机制**：多久没结论就升级（如 P1 15 分钟无进展 → 通知主管）
- **值班手册**：常见问题处置卡放在值班位（07 篇的场景卡就是干这个的）

## 5.7 自测与练习

1. 监控五层模型里，"RAID 卡电池失效"属于哪层？可能如何影响到第 5 层业务？（第 2 层硬件 → 写缓存失效 → 数据库 IO 暴降 → 业务超时）
2. 磁盘使用率告警不响的原因可能有哪些？（阈值太高/被静音/采集挂了/磁盘不在监控范围内——每种都要有排查动作）
3. "每晚备份成功"的邮件连续三个月都正常，还需要做什么？（恢复演练——备份的价值只有在恢复那一刻才被验证）
4. 容量报告里"按当前增速 47 天后磁盘满"，这叫哪类预警？（趋势预测——比静态阈值更早发现）
5. 变更单必须包含哪四要素？（改什么/为什么/影响面/回滚方案）

**动手练习**：
- 给你的训练场节点写一份"综合巡检脚本"（≥5 项检查），配 cron 每天跑；
- 做一次"恢复演练"：备份一个目录 → 删除 → 恢复 → 校验内容一致，写 3 行记录。
