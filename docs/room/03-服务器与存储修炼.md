## 3.1 服务器全生命周期管理

一台服务器从进机房到退役，每个阶段都有"专业动作"：

### ① 选型（买之前想清 5 年）

| 维度 | 关键问题 |
|---|---|
| 形态 | 1U/2U/4U？—— 2U 的 PCIe 扩展与散热是甜点区 |
| CPU | 核数 vs 频率：数据库吃高频、虚机吃核数 |
| 内存 | 通道插满优于单条大容量；预留插槽 |
| 存储位 | 前置盘位数（12×3.5" vs 24×2.5"）、NVMe 支持 |
| 网络 | 板载 10G？光口/电口？独立管理口必须 |
| 冗余 | 电源 1+1、风扇 N+1、RAID 卡缓存带电池/电容 |
| 维保 | 3 年 vs 5 年、备件响应时限（4 小时 vs 次工作日差很多钱） |

> 采购潜规则：**同型号批量买**——备件通用、固件统一、上架标准化。混搭型号是运维灾难。

### ② 验收入库

- 核对配置（CPU/内存/盘/网卡）与合同一致
- 记录序列号、管理口 MAC、快速登记进资产表
- **统一固件基线**：BIOS/BMC/RAID 卡固件刷到既定版本（新到货的批次固件往往五花八门）

### ③ 上架

- 按 U 位规划表执行（40-42U 放什么设备有讲究：轻的在上、重的在下、留散热缝）
- 双电源分别插 A/B 两路 PDU
- 管理口插管理网 VLAN
- 当场登记：位置/序列号/IP/管理口/用途

### ④ 在役管理

- **固件策略**：安全漏洞固件优先升级；功能固件按"测试机验证→维护窗口→分批"节奏
- **驱动/OS 基线**：同批同版本；变更走流程
- **资产核对**：季度盘点（实物 vs 台账），差异零容忍

### ⑤ 退役

- 数据销毁（见 06 篇：擦除 vs 消磁 vs 物理）
- 拆解可利用部件（内存/硬盘作备件）
- 环保回收（有资质的回收商 + 记录）
- 台账更新 + 维保注销

## 3.2 RAID 数学：把风险算明白

### 写惩罚（理解性能的钥匙）

| 级别 | 一次随机写带来的实际 IO | 说明 |
|---|---|---|
| RAID 0 | 1 | 无校验 |
| RAID 1 | 2 | 双写 |
| RAID 5 | **4**（读旧数据+读旧校验+写新数据+写新校验） | 小写入性能差 |
| RAID 6 | **6** | 更重 |
| RAID 10 | 2 | 镜像无校验 |

> 这就是"数据库用 RAID10 多过 RAID5"的数学原因。

### 重建时间估算

```
重建时间 ≈ 单盘容量 ÷ 重建速率
例：8TB 盘，重建速率 150MB/s → 8,000,000MB ÷ 150 ≈ 14.8 小时
（实际受业务 IO 竞争影响，可能 20-30 小时）
```

**重建期间是"最危险窗口"**：性能下降、且此时再坏一块 = 灭顶之灾。

### URE 与"双盘噩梦"（为什么大容量盘慎用 RAID5）

**URE（不可恢复读错误）**：磁盘扇区读不出来的概率。企业盘典型 1 per 10^15 bits（≈ 125TB 读取）。

RAID5 重建要**全盘读取所有存活盘**。以 4×8TB 的 RAID5 为例，重建需读 3×8TB = 24TB：

```
发生 URE 的概率 ≈ 24TB ÷ 125TB ≈ 19%
```

**近 1/5 的概率在重建时翻车**——这就是"大容量盘不要用 RAID5"的由来。结论：

- 小容量盘（≤2TB）：RAID5 可接受
- 大容量盘（≥4TB）：**RAID6（双校验）或 RAID10（镜像）**
- RAID6 重建同样有风险窗口，但容忍一块额外故障

### 热备盘（Hot Spare）策略

- **全局热备**：任意阵列坏盘自动顶上（推荐配 1-2 块）
- 热备盘 = 把"人工响应时间"降为零——凌晨坏盘也能自动开始重建
- 注意：热备盘平时不上电（或定期自检），定期验证其可用性

## 3.3 存储体系速成

| 类型 | 本质 | 场景 | 关键词 |
|---|---|---|---|
| DAS | 直连盘（服务器内置/JBOD） | 单机 | 简单快，不共享 |
| NAS | 文件级共享（NFS/SMB） | 共享目录、备份落点 | 开箱即用 |
| SAN | 块级网络存储（FC/iSCSI） | 数据库、虚拟化 | 高性能、要组网 |
| 分布式 | 软件定义（Ceph 等） | 云平台、海量 | 横向扩展、复杂度高 |

**iSCSI 三分钟实战概念**：
```
服务端（靶机）：建 LUN → 建 target → 绑定 IQN
客户端（发起端）：发现 → 登录 → 得到一块新"本地盘" → 分区挂载
```

**性能指标读法**：
- IOPS：每秒操作数（4K 随机最重要）
- 延迟：<1ms 佳、<5ms 可、>20ms 业务喊卡
- 队列深度与饱和度：高延迟 + 高队列 = 存储瓶颈实锤

**缓存与电池**：RAID 卡写缓存开"Write Back"性能大增，但必须配**电池/超级电容**（掉电时把缓存刷盘）——没有保护就是数据黑洞。

## 3.4 带外管理：从会用到自动化

### 单机操作（回顾 + 扩展）

```bash
ipmitool -H 192.168.10.11 -U admin -P '***' power status
ipmitool -H 192.168.10.11 -U admin -P '***' sdr            # 温度/电压/风扇
ipmitool -H 192.168.10.11 -U admin -P '***' sel list       # 硬件日志
ipmitool -H 192.168.10.11 -U admin -P '***' chassis status
ipmitool -H 192.168.10.11 -U admin -P '***' sensor list | grep -i temp
```

### 批量巡检脚本（思路示范）

```bash
#!/bin/sh
# bmc-inspect.sh — 批量读所有服务器带外温度与硬件告警
for ip in $(cat /etc/bmc-list.txt); do
  echo "== $ip =="
  ipmitool -H "$ip" -U admin -P "$BMCPASS" sdr type Temperature 2>/dev/null | \
    awk -F'|' '/degrees/ {gsub(/ /,"",$2); print "  温度:", $2, $5}'
  ipmitool -H "$ip" -U admin -P "$BMCPASS" sel list 2>/dev/null | tail -3
done
```
> 生产上密码不要明文放脚本——用环境变量/密钥管理。

### Redfish（现代带外 API）

新一代 BMC 提供 RESTful API（HTTPS + JSON）：
```bash
curl -k -u admin:pass https://192.168.10.11/redfish/v1/Systems/1
curl -k -u admin:pass https://192.168.10.11/redfish/v1/Chassis/1/Thermal
```
优势：结构化数据、易集成监控平台（比解析 ipmitool 文本优雅得多）。

### 带外网安全设计（红线）

- **独立 VLAN**：只允许管理终端访问，永不暴露公网
- 独立网段 + 防火墙策略 + 强密码/证书
- 变更后才开、用完即关的堡垒机通道
- 带外网被攻破 = 攻击者能"物理接触"你的服务器——最坏情况

## 3.5 故障预测：把"未病"治了

### SMART 关键属性（记住这 6 个）

| ID | 名称 | 含义 | 警戒 |
|---|---|---|---|
| 05 | Reallocated_Sector_Ct | 重映射扇区数 | >0 就要盯 |
| C5 | Current_Pending_Sector | 待处理扇区 | >0 立即备份+换盘 |
| C6 | Offline_Uncorrectable | 无法纠正 | >0 尽快换 |
| 187 | Reported_Uncorrect | 上报不可纠正错误 | >0 盯 |
| 197 | Current_Pending（部分厂商） | 同上 | >0 处理 |
| 198 | Offline_Scan_Uncorrectable | 离线扫描坏块 | >0 换 |

```bash
smartctl -a /dev/sda | grep -E 'Reallocated|Pending|Uncorrectable'
smartctl -H /dev/sda        # 健康状态一览
smartctl -t short /dev/sda  # 快速自检
```

### 硬件日志里的"征兆"

- `dmesg | grep -iE 'error|fail|mce'`：内存 ECC 错误、PCIe 错误
- 带外 SEL 日志：CPU 温度告警、电源事件、风扇转速异常
- **趋势思维**：单次告警看详情，**重复告警看趋势**——"这台机器三个月来温度告警了 5 次"比"一次红色告警"更值得处理。

### 预测性维护清单（月度动作）

- [ ] 所有盘 SMART 状态拉一遍，标记"变差"的盘
- [ ] 带外 SEL 日志聚合，找重复出现的告警源
- [ ] 风扇转速曲线对比（转速上升 = 积尘或轴承老化）
- [ ] 电源模块负载均衡检查（并机均流）
- [ ] 内存 ECC 错误统计（单根多错 = 该换）

## 3.6 硬件维护手艺（流程卡）

**换硬盘**：确认盘位（LED+界面）→ 拔旧插新 → 盯重建 → 记录序列号
**换电源**：确认冗余状态（另一路带载）→ 拔旧插新 → 确认面板恢复正常 → 记录
**换内存**：关机（或按手册热插支持）→ 防静电 → 按通道规则插 → BIOS 确认容量
**换风扇**：热插（多数机型支持）→ 注意手别碰叶片 → 确认转速恢复
**换 RAID 卡电池**：写缓存先切 Write Through → 更换 → 测回 Write Back

**工具与习惯**：
- 防静电手环、标签机、十字/内六角螺丝刀套装、手电、扎带、魔术贴
- **手机拍照记录**：拆之前先拍照，装回去时对照——省无数麻烦
- 螺丝分类盒：不同深度机箱螺丝混用 = 滑丝前奏

## 3.7 自测与练习

1. 8 块 4TB 盘，做 RAID5 + 1 热备，可用容量多少？（(8-1-1)×4 = 24TB；RAID6+热备 = (8-2-1)×4 = 20TB）
2. RAID 卡缓存电池坏了还开着 Write Back，最大风险是什么？（掉电瞬间缓存数据永久丢失 + 阵列可能不一致——立即切 Write Through）
3. 某盘 C5=16、C6=0，你的动作顺序？（① 立即确认备份完好 ② 标记该盘、安排更换 ③ 若在阵列中，换盘重建）
4. `ipmitool` 和 Redfish 的关系？（同一带外能力的两种接口：CLI vs REST API；新平台优先 Redfish）
5. 为什么采购要"同型号批量"？（备件通用、固件统一、操作肌肉记忆、轮换测试可行）
