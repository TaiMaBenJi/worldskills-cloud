# 精通之路 04 · 架构模式手册：35 张"条件反射卡"

> 语言流利靠句型，架构流利靠模式。
> 本篇是 35 张卡片，每张 = **触发场景 → 模式骨架 → 云上实现 → 典型坑**。
> 训练法：每天抽 3 张自问自答；练到"听到需求的那一秒，对应的模式自己跳出来"。

---

## A 组 · 伸缩与性能（7 张）

### A1 水平扩展 + 无状态服务
- **触发**：单机扛不住，要加机器
- **骨架**：把服务的"记忆"（会话/文件/缓存）移到外部存储 → 服务本身无状态 → 任意加副本
- **云上**：ASG/节点池 + LB + 外部会话存储（Redis）
- **坑**：本地文件/内存会话没外置——加了三台机器，用户还是各聊各的

### A2 缓存模式（Cache-Aside）
- **触发**：数据库读取压力大、热点数据反复查
- **骨架**：读：先查缓存→miss 查库→回填；写：先写库→失效缓存
- **云上**：ElastiCache/Redis、CDN、应用层本地缓存三级组合
- **坑**：缓存与库不一致（更新策略）、缓存雪崩（大量同时过期）、击穿（热点 key 失效瞬间打爆库）

### A3 CDN 分发
- **触发**：全球/全国用户、静态资源、视频图片
- **骨架**：源站 → 边缘节点缓存 → 用户就近取
- **云上**：CloudFront/阿里 CDN + 源站保护（OAC）+ 缓存策略
- **坑**：缓存刷新策略乱（发布后用户看到旧版）、动态内容误缓存

### A4 读写分离（CQRS 雏形）
- **触发**：读多写少（大多数业务都是）
- **骨架**：主库承接写 → 复制到只读副本 → 读全走副本
- **云上**：RDS 只读副本；进阶 CQRS（命令查询职责分离，读写两套模型）
- **坑**：复制延迟导致"刚写完读不到"——对一致性敏感的读仍要打主库

### A5 分片（Sharding）
- **触发**：单库单表大到极限（几亿行/写入爆炸）
- **骨架**：按业务键（用户 ID）把数据切到多个库/表
- **云上**：DynamoDB 天然分片；关系库需自己设计（或 Vitess/TiDB）
- **坑**：分片键选错（跨片查询地狱）、热点分片、再平衡痛苦

### A6 队列削峰
- **触发**：流量尖峰（秒杀/大促）、下游处理慢
- **骨架**：请求先入队 → 后端按自己节奏消费
- **云上**：SQS/Kafka/RocketMQ
- **坑**：队列积压无人知（要监控队列深度）、消息重复消费（要幂等）

### A7 目标追踪伸缩
- **触发**：负载波动大，手动扩容来不及
- **骨架**：设定目标指标（CPU 60%）→ 系统自动增减实例
- **云上**：ASG 目标追踪策略、K8s HPA、Karpenter
- **坑**：指标选错（内存型服务看 CPU）、扩容滞后（提前预热/预测伸缩）

## B 组 · 解耦与集成（7 张）

### B1 点对点消息（Queue）
- **触发**：任务队列、异步化、解耦生产者消费者
- **骨架**：生产者 → 队列 → 消费者（一条消息一个消费者处理）
- **云上**：SQS
- **坑**：忘了死信队列（毒消息卡死队列）、可见性超时设置不当（重复处理）

### B2 发布订阅（Pub/Sub）
- **触发**：一个事件多方关心（下单成功 → 通知库存/积分/物流）
- **骨架**：发布者 → 主题 → 多个订阅队列各自消费
- **云上**：SNS + SQS Fan-out 模式
- **坑**：订阅端故障丢消息（要死信+重放）、事件版本管理

### B3 事件驱动架构（EDA）
- **触发**：系统间耦合重、需要实时响应业务事件
- **骨架**：一切变化产生"事件" → 事件总线分发 → 各服务被动响应
- **云上**：EventBridge + Lambda（**韩国赛 task2 的核心**）
- **坑**：事件乱飞无治理（要 schema 规范）、调试困难（要事件追踪）

### B4 工作流编排
- **触发**：多步骤长事务（订单→支付→履约→通知，中途可能失败）
- **骨架**：状态机定义步骤 → 每步可重试/补偿（Saga 模式）
- **云上**：Step Functions、Argo Workflows
- **坑**：把"编排"写成"回调地狱"；补偿逻辑没设计

### B5 API 网关
- **触发**：多个后端服务要统一对外、要鉴权限流
- **骨架**：客户端 → 网关（鉴权/限流/路由/日志）→ 各服务
- **云上**：API Gateway、ALB+WAF、Kong/APISIX
- **坑**：网关成瓶颈（要能水平扩）、把业务逻辑塞进网关

### B6 幂等设计
- **触发**：任何会重试的系统（全部系统）
- **骨架**：每个操作带唯一 ID → 服务端去重表/状态机防重复执行
- **云上**：DynamoDB 条件写入、Redis SETNX
- **坑**：以为"网络不会重复"——网络一定会重复（重试/超时/用户刷新）

### B7 熔断与退避重试
- **触发**：依赖的下游不稳定
- **骨架**：重试要**指数退避 + 抖动**；连续失败触发熔断（快速失败）→ 半开探测恢复
- **云上**：SDK/框架层实现（如 Resilience4j）、服务网格自动熔断
- **坑**：无脑重试放大故障（重试风暴）、不配超时（无限等待）

## C 组 · 可靠性与容灾（7 张）

### C1 多可用区部署
- **触发**：要抵御机房级故障（底线要求）
- **骨架**：所有层（计算/数据/网络）都跨至少 2 个可用区
- **云上**：ASG 多 AZ、RDS Multi-AZ、ALB 多 AZ
- **坑**：只在计算层跨 AZ，数据库单点——白跨了

### C2 多区域容灾
- **触发**：抵御区域级故障；或全球低延迟
- **骨架**：四档方案（成本递增）：
  1. 备份恢复（RTO 小时级）
  2. 温备（Pilot Light，RTO 分钟级）
  3. 热备（Warm Standby，RTO 分钟级内）
  4. 双活（Active-Active，RTO≈0）
- **坑**：选了双活但数据同步没做对（脑裂）；DR 从没演练过 = 不存在

### C3 健康检查 + 自动故障转移
- **触发**：任何多实例系统
- **骨架**：LB 持续探测 → 不健康实例自动摘除 → 恢复后自动回归
- **云上**：ALB 健康检查、Route53 故障转移路由
- **坑**：健康检查路径太深（误杀）或太浅（假活——进程在但业务已死）

### C4 优雅降级
- **触发**：资源不足或依赖故障时，保核心弃边缘
- **骨架**：提前定义"哪些功能可以先死"（推荐挂了不显示推荐，下单必须活）
- **坑**：没有预案，故障时手动砍功能手忙脚乱

### C5 断路器（Circuit Breaker）
- **触发**：下游持续故障，避免白白消耗资源
- **骨架**：CLOSED（正常）→ 失败率超阈 → OPEN（快速失败）→ 定时 HALF-OPEN（试探）→ 成功回 CLOSED
- **坑**：断路器参数拍脑袋（要压测调参）

### C6 死信队列 + 重放
- **触发**：消息处理失败需要保留和人工干预
- **骨架**：失败 N 次 → 进死信队列 → 告警 → 修复后批量重放
- **坑**：死信没人看（等于黑洞）

### C7 备份与恢复（3-2-1 + 演练）
- **触发**：一切数据（勒索软件/误删/故障）
- **骨架**：3 份副本、2 种介质、1 份异地；**备份不验证 = 没有备份**
- **云上**：AWS Backup、跨区复制、生命周期策略
- **坑**：从没恢复演练过；备份和主数据在同一个账户（一起被删）

## D 组 · 发布与运维（7 张）

### D1 蓝绿部署
- **触发**：想零风险发布
- **骨架**：旧版（蓝）在线 → 新版（绿）完整部署验证 → 流量一键切换 → 出问题秒切回
- **成本**：双倍资源（发布窗口内）
- **坑**：数据库兼容性（新旧代码必须都能读同一份数据）

### D2 金丝雀发布
- **触发**：大版本、高风险变更
- **骨架**：新版本先接 1% 流量 → 观察指标 → 逐步 10%→50%→100%
- **云上**：ALB 加权目标组、Argo Rollouts
- **坑**：没配自动回滚判断标准（"看着没事"不是标准）

### D3 功能开关（Feature Flag）
- **触发**：代码要上线但功能要延后开放/随时关停
- **骨架**：代码里包一层开关 → 动态配置控制
- **坑**：开关堆积成技术债（定期清理已完成的开关）

### D4 基础设施即代码（IaC）
- **触发**：环境不一致、无法审计、重建困难
- **骨架**：所有基础设施用代码描述（Terraform/CFN）→ 版本管理 → 评审 → 自动应用
- **坑**：手动改线上（漂移）；state 管理不善

### D5 GitOps
- **触发**：K8s 环境要声明式、可审计的持续部署
- **骨架**：Git 是唯一事实源 → ArgoCD 持续调和 → 回滚 = revert commit
- **坑**：CI 里偷偷 kubectl apply（绕过 Git）——唯一的交付通道必须是 Git

### D6 不可变基础设施
- **触发**：服务器"越用越脏"、配置漂移
- **骨架**：永远不修改运行中的机器；要更新就构建"新镜像"替换旧的
- **云上**：Packer 镜像 + ASG 滚动替换
- **坑**：保留了 SSH 上去"临时修一下"的后门——纪律一破全破

### D7 可观测性三支柱
- **触发**：系统复杂到"猜不出问题在哪"
- **骨架**：Metrics（趋势）+ Logs（细节）+ Traces（链路），三位一体
- **坑**：只有监控没有日志（查不到根因）；告警太多全是噪声

## E 组 · 数据与 AI（4 张）

### E1 数据湖
- **触发**：要存原始数据（结构化+非结构化）、将来再分析
- **骨架**：原始层（S3）→ 清洗层 → 汇总层（分区+Parquet 格式）
- **坑**：变成"数据沼泽"（无治理无目录）；小文件问题

### E2 湖仓一体 / 数仓
- **触发**：湖上要做 SQL 分析、要事务保证
- **骨架**：S3 + 表格式（Iceberg/Hudi/Delta）+ 查询引擎（Athena/Trino/Spark）
- **坑**：当初为了"新潮"引入，团队没人会维护

### E3 流处理
- **触发**：实时性要求（实时风控/监控/推荐）
- **骨架**：Kinesis/MSK → 流计算（Flink/Spark Streaming）→ 实时结果
- **坑**：把"准实时"当"实时"设计；窗口/迟到数据策略缺失

### E4 RAG / 向量检索
- **触发**：让大模型基于"你的数据"回答
- **骨架**：文档切块→嵌入→向量库→检索相关块→拼进提示词→生成
- **坑**：检索质量差却怪模型；无评估集（改了 prompt 不知道是变好还是变坏）

## F 组 · 大系统与前沿（3 张）

### F1 单元化（Cell）架构
- **触发**：超大规模（百万级并发）、要限制故障爆炸半径
- **骨架**：把系统切成多个自包含"单元"（每个单元含全栈），用户路由到单元
- **案例**：饿了么、蚂蚁、Slack 都有类似架构
- **坑**：单元间共享组件（又粘回去了）

### F2 服务网格（Service Mesh）
- **触发**：微服务数量多，通信治理（mTLS/重试/观测）重复开发
- **骨架**：Sidecar（或 eBPF，无 Sidecar）接管所有服务间流量
- **坑**：为 5 个服务上网格（过度工程）

### F3 多云 / 混合云
- **触发**：避免锁定、合规要求、历史并购
- **骨架**：抽象层（K8s/Terraform）跨云统一；或"分层用云"（核心自建、边缘用公共云）
- **坑**：为了"多云"而多云——复杂度和成本翻倍，收益却模糊

## 附：模式选择决策框架（当多个模式都"可用"时）

**五问决策法**——任何架构选择，依次问：
1. **需求本质**：读多还是写多？强一致还是最终一致？实时还是异步？
2. **规模量级**：现在多少？三年后多少？（10 倍量级差异换架构；2 倍差异别折腾）
3. **约束条件**：团队会什么？预算多少？合规要求？（最先进 ≠ 最合适）
4. **失败模式**：这个选择会怎么坏？爆炸半径多大？有无逃生舱？
5. **演进路径**：要不要留升级接口？（打不过就换的方案，比一步到位更常赢）

**记住一句话**：**架构的成熟标志不是"用了多少高级模式"，而是"每个模式都能说出为什么用它、为什么不用别的"。**
