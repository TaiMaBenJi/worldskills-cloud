3. S3 Multi-Region Access Point

需求事项
  目前正在基于 Amazon CloudFront 与 CloudFront Function 等，实现按国家区分内容分发与恶意 User-Agent 拦截功能，通过提供静态内容并拦截自动化请求，来增强 Web 服务的安全性与性能。利用 AWS 的全球基础设施与边缘计算技术，构建快速、稳定的静态 Web 内容提供环境，是你的主要职责。
该题目在 ap-northeast-2、us-east-1 中创建资源。

VPC

为便于评分，创建默认 VPC 以构建云网络。

S3 Bucket

使用以下信息创建 S3 存储桶，并将发放的所有文件上传至 S3。这些文件之后必须能够通过 CloudFront 访问，且必须配置为 Lambda@Edge 以 SigV4 方式对请求进行签名，使 CloudFront 能够访问 S3 MRAP。此外，为了根据用户的地理位置从最近区域的 S3 存储桶提供内容，从而将网络延迟降至最低，请参考以下信息配置 Multi Region Access Point。MRAP 应启用 Public Access 阻止功能。

KR S3 Name Tag : skills-kr-cdn-web-static-<账户ID>

US S3 Name Tag : skills-us-cdn-web-static-<账户ID>

MRAP Name : skills-mrap

Bastion

为便于评分，使用 AWS EC2 在 ap-northesat-2 中创建 Bastion Server。为确保评分过程中 IP 不会突然变更，重启时也应配置为 IP 不变。Bastion 用于评分用途，因此必须确保通过 SSH 的访问与权限不存在问题。

Instance Name Tag : mrap-bastion

Machine Image : Amazon Linux 2023

Instance Type : t3.micro

Security Group Name Tag : mrap-bastion-sg

IAM Role Name Tag : mrap-bastion-role

Required Package : awscliv2 , curl, jq 

CloudFront Distributions

创建 Distributions 并进行用于全球内容传输的基本设置。源必须使用 MRAP，Viewer Protocol Policy 必须设置为 Redirect HTTP to HTTPS。Origin Request Policy 必须基于地区信息进行设置。此外，需开发并编写连接到 CloudFront 的 Viewer Request 阶段的函数代码。基于地区的拦截应利用 CloudFront 标头功能，对于来自 KR、US 国家以外的请求，以及 user-agent 标头中包含 bot、crawler、spider 的请求，配置为返回 403 Status 及以下响应。

CloudFront Name Tag : skills-global-distribution

CloudFront Function Name : skills-cf-function

Allow Region List : KR, US

Country 403 Status Body : “Access denied: unsupported country”

User Agent 403 Status Body :“Request blocked due to suspicious User-Agent”

CloudFront Invalidations

目前通过 CloudFront 发布的内容中，部分对象出现未能更新的问题。为解决此问题，需利用 Lambda 对该对象执行 CloudFront Invalidation 以使缓存失效，确保最新版本传递给用户，请参考以下信息进行配置。

KR Lambda Function Name : skills-lambda-function-kr

US Lambda Function Name : skills-lambda-function-us

KR Lambda IAM Role Name : skills-lambda-role-kr

US Lambda IAM Role Name : skills-lambda-role-us

VPC Lattice

该架构中 Consumer VPC 与 Service VPC 的网络相互隔离，两个 VPC 之间的通信通过 VPC Lattice 实现。Consumer VPC 中产生的请求经 VPC Lattice 传递至 Service VPC，从而实现安全、高效的网络连接。

Lattice Service Network Name : skills-app-service-network

Lattice Service Name : skills-app-service

Lattice Target Group Name : skills-alb-tg

应用程序

- Consumer Server (External ALB)

Consumer Server 位于 Consumer VPC 内的 Private Subnet 中，并连接到 External ALB。在接收来自外部客户端的请求后，将其通过 VPC Lattice 转发到 Service VPC，从而与 App Server 通信。通过这种方式，将外部流量安全地路由到内部服务。Consumer Server 应使用 Web 服务器，或使用 Python 直接开发来构建服务器。

External ALB 名称 : skills-consumer-alb

- App Server (Internal ALB)

App Server 位于 Service VPC 内的 Private Subnet 中，并连接到 Internal ALB。它接收通过 VPC Lattice 从 Consumer Server 转发来的请求，并处理业务逻辑。App Server 与 DynamoDB 集成以存储和查询数据，并提供可扩展性和稳定性。

Internal ALB 名称 : skills-app-alb

DynamoDB

App Server 使用 DynamoDB 处理数据。配置表时使用 PAY_PER_REQUEST 模式，并将 UserId 用作表的键。此外，为应对数据丢失，启用 PITR，并为防止表被意外删除而配置表的删除保护。

表名称 : skills-app-table

键 : UserId

模式 : PAY_PER_REQUEST

5. Actions Runner Controller

要求

  必须配置使用 EKS、Github、Github Actions、ArgoCD 的 CI/CD 流水线。构建在 EKS cluster 上运行的 Self-hosted Runner，以便执行 workflow job。不能使用 Github-hosted Runner。当容器镜像构建并上传到 ECR 后，必须通过 ArgoCD 使用上传的镜像对容器进行无中断部署。请根据要求配置合适的流水线。
该问题在 eu-central-1 中创建资源。

VPC 配置

为了分 dev 环境和 prod 环境运营，必须配置 2 个 VPC。

每个 VPC 必须存在 2 个 Public subnet、2 个 Private subnet。

VPC Name 标签: dev-vpc, prod-vpc

Bastion 配置

在 dev-vpc 的 Public subnet 中创建用于评分的 Bastion EC2，并且必须能够以集群管理员权限正常访问 EKS Cluster。此外，为了评分，必须能够通过 gh cli 访问 Github，并且必须已通过 argocd cli 登录到 ArgoCD。

为了评分，必须向实例 iam role 添加 AdministratorAccess 策略。

Bastion EC2 安装包: kubectl, gh cli, argocd cli

Bastion Name 标签: dev-bastion

应用程序

应用程序在 8080 port 上运行。

应用程序必须通过 Argo Rollouts CRD 部署到每个 EKS cluster。

应用程序必须部署到每个 EKS cluster 的 app namespace 中。

EKS

必须分别在 dev 和 prod 分离的 2 个 VPC 的 Private subnet 中配置 EKS cluster。

使用名为 dev-cluster、prod-cluster 的 cluster name。

Repository

使用 Github 配置用于应用程序开发和版本管理的 Public Repository。

创建名为 day2-product 的 Repository。

将名为 app 的 Helm chart 配置在 Repository 最顶层位置的 charts/ 中，并将 dev.values.yaml、prod.values.yaml 配置在 values/ 中。

在 main branch 中，将应用程序源代码及部署管理环境配置所需的 .github/workflows、Dockerfile、app.py、requirements.txt、charts/、values/ 一起 commit & push。

以 main branch 为 source 创建 dev、prod branch。另外，将 dev branch 设置为 base。

可以为新功能添加 feature/* 形式的 branch，并可以向 dev 及 prod branch 创建 PR。

创建名为 approval 的 PR label，用于处理向 prod branch 发起的 PR 请求。

Registry

在 ECR 中创建 product/dev、product/prod 这 2 个 private repository。

必须预先上传通过提供的 Python 源代码构建的镜像。

Workflow

配置使用 Github Actions 的流水线。

必须编写 2 个名为 dev、prod 的 workflow，并分别编写为 dev.yml、prod.yml。

workflow 必须配置为考虑多架构，能够同时构建 linux/amd64、linux/arm64。此外，新构建镜像的 tag 使用 Commit ID。

当 Trigger 发生时，将新 tag 的镜像上传到 product/dev、product/prod ECR repo 后，修改 Repo 内 values/ 的 dev/prod.values.yaml 以使用新镜像，并通过 argocd sync 自动完成整体工作，使其在各个 cluster 中更新为新版本。

必须在 dev、prod cluster 中分别配置各自的自托管 Runner，runner 必须分别具有 dev、prod 这个 custom label。此外，必须维持 2 个 runner。

在 feature/* branch 向 dev branch 创建 PR 时，使用 dev-cluster 的 runner 在 1 分钟内 merge 到 dev branch，并 build & push 到 product/dev ECR repo 后，立即 Sync 到 ArgoCD。

在 dev branch 向 prod branch 创建 PR 时，如果为该 PR 赋予 approval label，则在 1 分钟内 merge 到 prod branch，并 build & push 到 product/prod ECR repo 后，立即 Sync 到 ArgoCD。此外，必须 Fast-Forwarding 到 dev branch。

请良好配置 Dockerfile，使流水线在 1 分钟内成功完成。

在 ECR push 时，为了访问 ECR 时的安全，不能使用 AWS Access Key。配置 Github OIDC，使 workflow 能够通过 IAM Role 访问。

Argo

ArgoCD 仅安装在 dev-cluster 中。prod-cluster 只能安装 Rollouts，并将其注册到位于 dev-cluster 的 ArgoCD 中，以便一起管理。此外，必须使用名为 argocd 的 namespace。

应用程序必须通过 Blue/Green 部署策略进行更新，并禁用 Auto sync。由于 Workflow 中的 Sync，当新版本的应用程序准备完成后，必须自动替换现有应用程序。

应用程序更新完成后，现有应用程序 pod 必须终止。

Rollout 资源的名称配置为 product。

ArgoCD Application 的名称分别配置为 dev、prod。

ALB

必须按环境配置 2 个 ALB，以便能够通过 ALB 访问最新应用程序。

   - Ingress Name : dev-ingress, prod-ingress

   - Ingress Namespace : app

   - ALB Name Tag : dev-alb, prod-alb
